## 二、TDD设计评审与建议

### 2.1 实施难度评估

| 挑战项 | 难度 | 分析 |
|--------|------|------|
| 状态机覆盖率 90% | **高** | 分支多，需要大量边界测试 |
| 前端 Canvas 测试 | **高** | React Flow渲染测试困难 |
| 异步执行测试 | **中** | Testcontainers可解决 |
| 多租户测试隔离 | **中** | 租户ID前缀隔离可行 |

### 2.2 关键建议

**建议1：降低状态机覆盖率目标至80%**

理由：
- 90%覆盖率在复杂状态机中难以稳定达成
- 建议分为核心路径（85%）+边界路径（60%）分开考核

**建议2：前端测试聚焦逻辑层**

理由：
- Canvas渲染测试投入产出比低
- 建议只测试GraphManager布局算法等纯逻辑

## 三、安全设计评审与建议

### 3.1 资源需求评估

| 安全功能 | 人天估算 | 实施建议 |
|----------|----------|----------|
| 基础JWT认证 | 5人天 | MVP必需 |
| RBAC权限控制 | 8人天 | MVP必需 |
| MFA支持 | 15人天 | 延后至二期 |
| Webhook签名 | 5人天 | MVP必需 |
| 敏感数据加密 | 10人天 | MVP必需 |

### 3.2 关键建议

**建议3：安全功能分阶段实施**

| 阶段 | 安全功能 | 人天 |
|------|----------|------|
| MVP | JWT + RBAC + 基础限流 + Webhook签名 | 18 |
| 二期 | MFA + OAuth2 + 敏感数据加密 | 20 |
| 三期 | ABAC + 高级审计 | 25 |

**建议4：简化ABAC模型**

理由：
- 完整ABAC实现复杂度高
- 建议MVP阶段只实现RBAC + 简单资源所有者检查

---

## 四、架构设计评审与建议

### 4.1 资源需求评估

| 服务/组件 | 建议调整 |
|-----------|----------|
| node-service | MVP可合并至executor |
| executor-service | 根据负载调整副本数 |

### 4.2 关键建议

**建议5：MVP阶段合并node-service**

理由：
- node-service独立部署增加复杂度
- MVP阶段节点数量有限

**建议6：执行引擎技术栈调整**

理由：
- Vert.x学习曲线较陡
- 建议MVP阶段使用Spring Boot ThreadPool

**建议7：数据存储简化**

理由：
- Kafka在MVP阶段使用率低
- 建议先使用Redis Stream

## 五、整合后的MVP实施计划

### 5.1 调整后的MVP范围

| 模块 | MVP范围 | 延后项 |
|------|---------|--------|
| 流程编排 | 可视化编辑器 + 4种基础节点 + 变量系统 | 条件分支延至二期 |
| 执行引擎 | 队列调度 + 节点执行 + 执行控制 | 并行执行延至二期 |
| 触发系统 | Webhook + 定时 + 手动 | - |
| 安全 | JWT + RBAC + 基础限流 | MFA/OAuth2/ABAC |
| 测试 | 单元测试 + 核心API集成测试 | E2E部分场景延后 |

### 5.2 调整后资源估算

| 角色 | 人数 | 周期 | 人月 | MVP成本 |
|------|------|------|------|----------|
| 前端工程师 | 2 | 6周 | 3 | ¥90,000 |
| 后端工程师 | 2 | 6周 | 3 | ¥105,000 |
| 技术负责 | 1 | 6周 | 1.5 | ¥75,000 |
| UI设计 | 1 | 3周 | 0.75 | ¥22,500 |
| **合计** | | | **7.25** | **¥292,500** |

**成本变化**：从¥345,000降至¥292,500（降低15%）

## 六、实施风险与缓解

| 风险 | 缓解措施 |
|------|----------|
| 异步执行测试困难 | 使用Testcontainers + Redis Mock |
| 状态机覆盖率不达标 | 降低目标至80% |
| Vert.x学习成本高 | MVP使用ThreadPool方案 |
| 安全功能开发量大 | 优先实现核心功能，延后MFA/OAuth |

---

## 七、待讨论问题

1. **状态机覆盖率目标**：90%是否合理？建议降至80%
2. **Vert.x技术选型**：是否调整为Spring Boot ThreadPool？
3. **Kafka引入时机**：MVP是否需要Kafka？
4. **E2E测试范围**：是否只覆盖核心场景（创建+执行）？

---

## 八、总结

第二轮设计评审结论：

1. **TDD设计** 整体完善，但覆盖率和前端测试策略需调整
2. **安全设计** 过于完善，建议分三期实施，MVP聚焦核心功能
3. **架构设计** 复杂度偏高，建议MVP阶段简化

调整后MVP预计：
- **周期**：6周
- **成本**：¥292,500（降低15%）
- **覆盖率目标**：80%（整体）/ 90%（核心模块）
- **安全**：JWT + RBAC + 基础防护
